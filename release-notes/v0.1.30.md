# v0.1.30 — a live reload no longer drops a member's tool policy and persona

Release on npm `latest`; recommended host: Harness `0.2.1-rc.3`. This release fixes one defect in this line, found by running the repository's own real-host runtime suite. No host-facing plugin API changed and no dependency moved.

## What was wrong

A live reload of this plugin — the `patchReload: "live"` path a profile takes when the entry is reconfigured, or any plugin patch — left every already-running member **unrestricted**: its captain-only tools became visible and executable, and its persona section rendered empty. The captain-only admission check that failed afterwards was a different mechanism (per-agent capability scopes), which is why the denial could look intact while the member's own filter was gone.

Measured on the packed artifact against a real `0.2.1-rc.3` host, `stability` scenario, before the fix:

- `fresh` phase: `lab_forbidden` hidden, executing it answered `unknown tool "lab_forbidden"` (`ToolNotFoundError`/`UNKNOWN_TOOL`).
- after `entry.update({config: …})` + `entry.fiber.await()`: the same live Agent, the same tool **visible**, and executing it actually ran (`Forbidden tool executed`); the role marker in the member's persona section went from 1 occurrence to 0.

The host `0.2.1-rc.3` and the previous one both reproduce it, so it is not a host regression.

## Root cause

Live-member hydration validates a member's saved filter against the registered tool registry: `tools.restrict()` rejects a filter naming a tool it does not know, rather than installing it. In `registerAgentTeamsTools` the hydration call (`installMemberSelectionRuntime`) sat **before** the registration of `agent_teams_set_member_model` — the 15th and last tool, added in this line. At activation time that tool therefore did not exist yet, the saved `deny` list named it, `restrict()` threw, and the non-vetoable activation path swallowed the error into a warning plus a request-reject listener. The member kept a request-reject listener instead of a filter, which is also why the two later scenario phases (`steering`, `reassign`) and everything after them collapsed: the member could no longer take a turn at all.

## Fix

`src/tools.ts` calls `installMemberSelectionRuntime` after **every** `ctx.tools.register(...)` in that function, with the ordering invariant written down at the call site. Nothing else changed: the spawn path still installs the same filter through the same seam, and the persona section is installed by the same code immediately after it.

Guarded twice:

- `scripts/verify.mjs` gains a source-scan check, "every tool registration precedes live-member hydration, so a saved member filter always resolves" — a tool registered after the hydration call fails the offline gate instead of silently disarming every live member.
- The repository's real-host `stability` scenario is the acceptance test: it reconfigures the live entry, awaits the new fiber, and then asserts the member's filter, its persona section, and admission of a captain-only tool, all against the same live Agent.
